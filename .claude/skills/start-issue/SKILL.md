# Issue に着手する

Issue #$issue に着手する。目的は、**実装の前に、ユーザーが「何を・なぜ・どう作るか」を自分の言葉で説明できる状態にすること**。Spotee は就活のメインプロダクトなので、面接で説明できる水準を目指す。

現在のブランチと作業ツリー:

- ブランチ: !`git -C "${CLAUDE_PROJECT_DIR}" branch --show-current`
- 未コミットの変更: !`git -C "${CLAUDE_PROJECT_DIR}" status --short | grep -v '^??' | head -20`

## 1. 読む

1. `gh issue view $issue` で Issue を読む。親子関係や関連 Issue があれば、それも読む
2. 実装方針のメモがあれば読む（`CLAUDE.local.md` に場所がある）。無ければ読まずに進めてよい
3. 関係するコードを読む。推測で解説しない

## 2. ブランチを切る

未コミットの変更が無いことを確かめてから、最新の main から切る。

- 名前: `feat/<短い英語>`・`fix/<短い英語>`・`chore/<短い英語>`
- 未コミットの変更があれば、先にどうするかユーザーに確認する

## 3. 解説する

- **用語の定義から**始める。ユーザーの前提知識を仮定しない
- 「何を作るか」「なぜ必要か」「どう作るか（選択肢と、それぞれのトレードオフ）」の順に書く
- 選択肢が複数あるなら、推奨とその理由を示す
- 表や短いコード片を使い、要点を絞る

## 4. ユーザーに説明してもらう

解説のあとに、2〜4問の問いを出す。

- 「どのテーブルに何を足すか」「この設計で何が守れるか」のように、**実装内容を自分の言葉で説明させる**問いにする
- 答えるのに必要な材料は、解説の中で先に渡しておく
- ここで止まり、ユーザーの回答を待つ

## 5. 回答を確かめて合意する

- 合っている点・足りない点・誤っている点を、理由とともに返す
- 誤解があれば、その場で解説を補う
- 実装方針を短く確定させ、**ユーザーが実装を頼んでから**実装に入る

ユーザーが「実装を先に」と言った場合は、3〜5 を飛ばして実装してよい。その場合は、`/finish-issue` の前に解説と問いを行う。
