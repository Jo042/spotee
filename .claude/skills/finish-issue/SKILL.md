# 実装を仕上げる

実装が終わった作業を、PR と記録まで仕上げる。**作業中に見つかった問題を1つも埋もれさせない**ことと、**PR 本文を簡潔に保つ**ことを優先する。

現在の状態:

- ブランチ: !`git -C "${CLAUDE_PROJECT_DIR}" branch --show-current`
- main からのコミット: !`git -C "${CLAUDE_PROJECT_DIR}" log --oneline main..HEAD | head -20`
- 変更ファイル: !`git -C "${CLAUDE_PROJECT_DIR}" status --short | grep -v '^??' | head -30`

`/start-issue` で解説と問いを飛ばしていた場合は、先にそれを行ってから進める。

## 1. 検証する

変更の範囲に応じて実行し、結果を記録しておく（PR に書く）。

- 常に: `npm run lint`・`npm run test`・`npm run build`
- `CLAUDE.md` の「テストとマージの基準」に沿ったテストがあるか。`/start-issue` で承認したテストケースがすべてテスト（または人の確認手順）になっているか
- `schema.prisma` を変えた: マイグレーションを作ったか。`npm run db:status` で適用状況を確かめる
- GraphQL の型を変えた: バックエンドを起動して `schema.gql` を更新し、`npm run codegen`
- 画面を変えた: 実際のブラウザで確かめる（スマホ幅も）。テスト用のセレクタは一意に当たるものを使う
- API を変えた: 実際のサーバーに対してリクエストを送って確かめる。確かめているサーバーが今の変更を反映したものか（ポートと PID）を確認する

失敗したら直してから進む。直せないものは、その旨をユーザーに伝える。

この変更で古くなった記述がないかも確かめる。コマンド・パス・設計の決定・画面の部品を変えたなら、`CLAUDE.md`・`README.md`・スキル・`DESIGN.md` の該当箇所を**同じ PR で**直す（CLAUDE.md とスキルは差分を示して承認を得る）。

## 2. 見つかった問題を仕分ける

この作業の中で見つけた問題・気づき・後回しにしたことを、すべて列挙してから仕分ける。

| 種類 | 行き先 |
|---|---|
| この PR の範囲で直すもの | 直してからコミットする |
| いずれ直す必要があるもの | **公開の Issue に起票する**（ラベル `found-during` と種類・領域のラベル）。PR 本文に書くだけにしない |
| セキュリティに関わるもの | 公開しない。非公開の記録に書く（`CLAUDE.local.md` を参照） |
| 直さないと決めたもの | 理由とともに非公開の記録に残す |

## 3. コミットする

- 1行の Conventional Commits: `<type>(<scope>): <日本語の説明>`
- 1つのコミットに1つの論理的な変更。無関係な変更を混ぜない
- ステージする前に `git status` を見て、秘密情報（`.env` など）や無関係なファイルが入っていないか確かめる。ファイルは名前を指定して追加する

## 4. PR を作る

- `.github/PULL_REQUEST_TEMPLATE.md` に沿って書く。**「何を・なぜ・どう確かめたか」だけ**を短く書き、判断の経緯の詳細は書かない。「確かめたこと」には自動・機械的に確かめたことだけを書き、人の確認手順は書かない
- `Closes #<issue>` を入れる。2 で起票した Issue の番号も「見つかった問題」の欄に書く
- push して PR を作り、CI の結果を待って報告する
- 別の PR の上に積む場合は、マージの順番を本文の冒頭に書く
- **非公開で管理している問題（セキュリティなど）を直す PR**: 関連 Issue は「なし」にする。コミットと PR 本文は何を変えたかだけを中立に書き、再現手順・攻撃の方法・防御の数値は書かない。マージ後に、非公開の Issue を手で閉じ、記録の状態を修正済みにする

## 5. 人の確認手順を残す

画面や操作に関わる変更なら、ユーザーが手と目で確かめる手順を、非公開の確認待ちリストに追記する（場所と書式は `CLAUDE.local.md`）。PR には書かない。

- 前提（どのアカウント・どのデータ・どの環境で。フロントだけの変更なら Vercel のプレビューでよい）
- 手順と、期待する結果
- 見てほしい観点: 文言は自然か、押しやすいか、待たされないか、失敗したときにどうなるか、スマホと PC で違和感はないか

## 6. 学習記録を残す

非公開の記録として、テーマごとに学習記録を書く（場所と書き方は `CLAUDE.local.md`）。

- 1つの PR から、学べたことのテーマごとに1〜3件
- 着手時に「土台の知識」を解説したなら、それは機能の記録と分けて1件にする（あとで基礎だけを読み返せるように）
- 複数の案から選んだ判断は、学習記録とは別に判断の記録にする
- 「用語の整理」「学んだこと（なぜそうなるか）」「詰まった点と解決策」を必ず書く
- 書いたら索引を更新し、非公開のリポジトリに push する

## 7. 報告する

- PR の URL と CI の結果
- 起票した Issue と、非公開の記録に書いたもの
- 確認待ちリストに足したもの
- ユーザーに確かめてほしいこと（本番でしか確かめられないことなど）
