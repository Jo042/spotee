# infra

**性能検証用の環境定義を置く場所。本番インフラではない。**

Spotee の本番は Vercel（フロントエンド）/ Railway（API）/ Supabase（DB・認証・ストレージ）で動いており、それらの構成はコード管理していない。ここにあるのは、計測のために立てて終わったら壊す使い捨ての環境である。

## 構成

| ディレクトリ | 用途 | 何を測るか |
|---|---|---|
| [bench/](bench/) | ローカルの PostgreSQL コンテナ | 実行計画・インデックス設計・クエリ単体の実行時間 |
| `aws/` | AWS 負荷検証環境（OpenTofu / EC2 + RDS + ALB） | 同時実行下の p95・スループット・コネクションプール・CPUクレジット |

## なぜ環境を分けているか

測りたいものが違うため。

**実行計画の分析は PostgreSQL 内部の処理時間を見る作業**で、ネットワークやインスタンス構成の影響を受けない。むしろ AWS の db.t3.micro は burstable CPU なので、クレジットが減るにつれて性能が変化し、「インデックス A と B のどちらが速いか」という比較の土台にならない。インデックスを貼っては消す試行を高速・無償で回せるローカルが適している。

一方、**同時実行・リソース制約・ネットワーク遅延はローカルでは再現できない**。アプリと DB が同一マシンにあると RTT がほぼ 0 になり、N+1 の影響を過小評価する。こちらは AWS で測る。

同じ「CPU クレジットの枯渇」という現象が、クエリ比較ではノイズ、負荷試験では観測対象になる。だから目的別に環境を分ける。
